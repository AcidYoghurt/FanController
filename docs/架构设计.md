# Linux Thermal Control 架构设计

## 1. 进程边界

```text
Qt Quick GUI（普通用户）
        │ system D-Bus + Polkit
        ▼
FanService（root systemd 服务）
        │
        ▼
FanController
├── HwmonBackend
├── ThermalZoneBackend
├── ThinkPadBackend
├── IdeaPadBackend
├── ClevoBackend
├── NvidiaBackend
└── MockBackend（仅显式开发模式）
```

GUI 永远不直接打开 `/sys/class/hwmon/*/pwmN` 或 `/proc/acpi/call`。守护进程只暴露高层模式和曲线 API，避免界面传入任意文件路径或原始 EC 命令。

## 2. 通用数据模型

共享数据位于 `src/common/ThermalTypes.h`：

- `TemperatureSensor`：稳定 ID、后端、设备、种类、温度、可用状态；
- `FanDevice`：RPM、占空比、只读/可控、自动/全速/曲线能力；
- `FanZone`：控制器、绑定传感器、目标风扇、安全约束；
- `BackendInfo`：驱动、状态、说明和能力集合；
- `Result`：结构化错误代码和消息；
- `ControlMode`：仅 `Automatic`、`FullSpeed`、`CustomCurve`。

稳定 ID 示例：

```text
hwmon:amdgpu:0000_05_00_0:temp1
hwmon:nct6798:platform_nct6775_656:fan2
clevo:CLV0001:fan0
nvidia:00000000_01_00_0:temperature
```

界面侧不再使用匿名 `QVariantList` 下标猜测 CPU 风扇。`InventoryModels.*` 将 D-Bus 数据转换为具有固定 roles 的 `QAbstractListModel`。

## 3. 后端接口

```cpp
class IFanBackend {
public:
    virtual BackendInfo info() const = 0;
    virtual bool probe() = 0;
    virtual void refresh() = 0;
    virtual QList<TemperatureSensor> sensors() const = 0;
    virtual QList<FanDevice> fans() const = 0;
    virtual QList<FanZone> zones() const = 0;
    virtual Result setAutomatic(const QString &zoneId) = 0;
    virtual Result setFullSpeed(const QString &zoneId) = 0;
    virtual Result setDuty(const QString &zoneId, int percent) = 0;
};
```

### HwmonBackend

扫描 `/sys/class/hwmon/hwmon*`：

- `tempN_input` / `tempN_label`；
- `fanN_input` / `fanN_label`；
- `pwmN` / `pwmN_enable`。

仅当 `pwmN` 和 `pwmN_enable` 同时存在并可写时声明为可控。当前按 Linux hwmon 常见语义使用：

```text
pwmN_enable = 1  手动 PWM
pwmN_enable = 2  自动控制
pwmN        = 0..255
```

这使 `thinkpad_acpi`、`dell_smm_hwmon`、AMDGPU、部分 ASUS/Acer/MSI 平台驱动和主板 Super-I/O 在内核提供标准属性时能够自动工作。若驱动只提供温度或 RPM，则保持只读。


### ThermalZoneBackend

当 `coretemp`、`k10temp`、`amdgpu`、`i915` 或 `xe` 没有通过 hwmon 提供 CPU/GPU 温度时，扫描 `/sys/class/thermal/thermal_zone*` 作为只读回退。已有同种类 hwmon 传感器时不会重复添加。

### ThinkPadBackend

检测 `/proc/acpi/ibm/fan`。只有以下条件同时满足时才声明可控：

```text
/sys/module/thinkpad_acpi/parameters/fan_control = Y/1
/proc/acpi/ibm/fan 可写
commands 字段明确包含 level
```

自动模式写入 `level auto`；曲线将百分比映射到 1–7；只有驱动明确列出 `full-speed` 时才启用满速。未开启内核写权限时保持只读。

### IdeaPadBackend

识别 `VPC2004/physical_node/fan_mode` 和标准 `platform_profile`。`fan_mode` 的 EC 返回值与可写值在不同 IdeaPad/ThinkBook 固件上并不一致，并且不提供 RPM 或可靠的原状态恢复语义。因此当前后端只报告“固件管理”，不把 `4` 或 `performance` 虚假标记为 100% 满速。

部分固件会返回不透明的 `fan_mode` 数值，写入后也不保证读回相同值。缺少 RPM 或明确的原状态恢复语义时，软件保持只读，不从平台性能配置推断风扇转速。

### Apple SMC（HwmonBackend）

Intel Mac 的 `applesmc` 和 Apple Silicon 的 `macsmc_hwmon` 若同时公开以下属性，将作为安全可控区域：

```text
fanN_input
fanN_min
fanN_max
fanN_manual
fanN_output 或 fanN_target
```

自动模式写 `fanN_manual=0`；手动和曲线模式先写 `fanN_manual=1`，再把百分比映射到 `fanN_min..fanN_max` 的目标 RPM；满速写设备报告的最大 RPM。缺少任一关键属性时只读取遥测，不访问原始 SMC key。

### ClevoBackend

只在以下条件全部满足时探测成功：

```text
DMI vendor  = COLORFUL
DMI product = P16 TA 24
ACPI device = CLV0001 / DCHU
/proc/acpi/call 可写
```

保留实机验证命令：

```text
\_SB.WMI.WMBB 0x0 0x68 ...         设置占空比/全速
\_SB.WMI.WMBB 0x0 0x69 0x0000000f 恢复自动
```

### NvidiaBackend

优先动态加载 `libnvidia-ml.so.1`，避免构建环境强制依赖 NVIDIA SDK。使用 NVML 查询 GPU、温度、风扇数量、百分比、RPM 和设备公开的最小/最大速度。

只有以下 API 同时存在且设备调用成功时才创建可控区域：

```text
nvmlDeviceGetNumFans
nvmlDeviceGetMinMaxFanSpeed
nvmlDeviceSetFanSpeed_v2
nvmlDeviceSetDefaultFanSpeed_v2
```

自动模式使用 `nvmlDeviceSetDefaultFanSpeed_v2` 归还驱动策略；满速使用设备报告的最大值；曲线按同一百分比范围控制。笔记本或受限驱动若返回不支持/无权限，则不创建控制区域，并退回 NVML 或 `nvidia-smi` 只读遥测。若 GPU 另有内核 hwmon PWM，也仍可由 `HwmonBackend` 发现。

### Intel/AMD GPU

- AMDGPU：通常通过 DRM 设备关联的 `amdgpu` hwmon 出现；
- Intel iGPU：若 `i915`/Xe 驱动提供 hwmon 温度则读取；
- 没有独立物理风扇的 iGPU 不会被虚构成 GPU 风扇，其散热归 CPU/系统风扇区域所有。

## 4. 后端聚合与冲突原则

探测顺序：

1. 已验证、严格白名单的专用后端；
2. 标准 Linux hwmon；
3. 只读厂商遥测后端。

同一后端只控制自己声明的 `zoneId`。没有安全写接口的设备永远不会进入 `FanZone`。全速模式遍历全部可控区域；任何只读通道只影响“部分支持”状态，不会导致模式伪失败。

## 5. 自定义曲线

曲线按 `zoneId` 保存到：

```text
/var/lib/linux-thermal-control/curves.json
```

每个区域保存 2–32 个点，默认配置包含十个点。保存前会检查温度严格递增、占空比不下降，以及固定的满速安全端点。控制循环：

1. 每秒刷新传感器；
2. 取最近八次有效读数的算术平均值作为曲线控制温度；
3. 目标占空比与当前值相差至少 4% 时才调整；
4. 普通升速每秒最多增加 2%，降温需求持续 5 秒后每秒最多降低 2%；
5. 控制平均温度达到安全阈值后平滑升至 100%；
6. 原始温度进入硬件上限前 5°C 或传感器失效时，立即切换为 100%。

## 6. D-Bus API

服务端点：

```text
org.linuxthermal.Control1
/org/linuxthermal/Control1
```

主要方法：

```text
GetStatus()                         -> inventory + state + mode + profiles
SetMode(mode)                       -> automatic/full-speed/custom-curve
GetCurveProfiles()
GetZoneCurve(zoneId)
SetZoneCurve(zoneId, points)
ApplyZoneCurve(zoneId, points)
ResetZoneCurve(zoneId)
```

`GetCurve/SetCurve/ApplyCurve/ResetCurve` 是面向首个可控区域的单区域便捷接口。

## 7. 前端状态

界面状态包括：

```text
probing
ready
degraded
unsupported
disconnected
fatal-error
```

叶组件只接收属性并发出信号，只有 `Main.qml` 访问 `LinuxThermal.Backend` 中的 `FanBackend` 单例，其余页面通过属性注入后端。曲线编辑模型具有 `dirty` 和 `conflict` 状态，远端更新不会覆盖未保存编辑。


前端现拆分为 `linux-thermal-control` 启动入口、`linux-thermal-client` D-Bus 模块和 `linux-thermal-ui` QML 模块。`state/AppController.qml` 管理页面交互状态，`state/AppSettings.qml` 管理外观偏好，`Theme.qml` 提供视觉令牌。模块依赖、视觉规范与测试方法见 [前端结构与视觉规范](frontend.md)。
